# Second-Brain Wiki + Graph RAG

## Why this exists

A chatbot that re-reads "here's everything relevant right now" every turn only ever knows the most recent snapshot — anything from two weeks ago is gone unless someone happens to re-paste it. A second brain flips that: every worthwhile result becomes a permanent, searchable note, and the system gets more useful the longer it's used, without needing a vector database or an embedding model. That last part matters most for local-first, small-model setups — the retrieval method here is pure keyword scoring + link-graph traversal over the filesystem, so it stays fast and cheap even on a laptop running a 2B–12B local model.

This pattern was reverse-engineered from the user's own working systems (`connect-ai`, a VS Code extension, and `eery1677-wiki`, their real day-to-day knowledge vault) — it is proven, not theoretical. One real gap was found in that reference implementation during review: it never checks whether a newly-created note is actually faithful to its source before saving and pushing it. Section 5 below exists specifically to close that gap — don't skip it.

## The six pieces

Build these roughly in this order; each is independently useful, so a partial build still pays off.

### 1. Storage — two folders, not one

```
{brain_dir}/
├── 00_Raw/{date}/original.md      ← verbatim ingested source, untouched
└── 10_Wiki/
    ├── Topics/
    ├── Projects/
    ├── Skills/
    └── Decisions/
```

`00_Raw` is the paper trail — whatever came in (a pasted article, a generated report, a video transcript) gets saved exactly as-is, dated. `10_Wiki` holds the AI-restructured notes that actually get retrieved later. Keeping raw and structured separate means a bad restructuring pass never destroys the original, and gives the verification step (§5) something concrete to check against.

Every wiki note needs this frontmatter + section shape — see `references/note-schema.md` for the full spec and a worked example:

```yaml
---
id: <uuid>
category: "[[10_Wiki/Skills]]"
confidence_score: 0.9
tags: [tag1, tag2]
last_reinforced: 2026-08-31
---
## 📌 One-line insight
## 📖 Structured knowledge
## ⚠️ Contradictions & updates
## 🔗 Links (Parent / Related / Source)
```

The category and links use `[[wikilink]]` syntax — that's not decoration, it's the graph that §3 traverses.

### 2. Ingestion — raw in, structured note out, with a checkpoint

Something worth remembering shows up (user pastes a file, or a feature in the app produces output worth keeping) → save it verbatim to `00_Raw/{date}/`. Then **ask before structuring** — "want me to turn this into a knowledge note?" — rather than doing it silently. This isn't just politeness: it's the moment the user can say "no, that run was garbage, don't keep it," which is cheaper than fixing a bad note after the fact.

On confirmation, one LLM call reads the raw content and produces the structured note (frontmatter + sections above), choosing its own category/tags/wikilinks to existing notes. Use structured/JSON output if the target stack supports it (more reliable than parsing markdown back out of freeform text) — see §5 for why this call should also carry the verification check, not just the note content.

**Wire the save button into every stage whose reasoning matters, not just the final deliverable.** It's tempting to only add "save to brain" where a pipeline's *end product* appears (the finished article, the generated song, the final report) — but if an earlier stage is what actually explains *why* that output looks the way it does (a trend/competitive analysis that a later creative-generation stage is grounded in), skipping it leaves a real gap: the assistant can recall *what* was made but not *why*, because the reasoning never became a note. Caught in production: a chatbot could describe a generated song's lyrics and prompts in detail but had no way to answer "why did we pick this topic for this song" — the upstream channel analysis that the topic was chosen from was durably saved to its own history log (for trend computation), but was never wired into the wiki at all. Don't duplicate the full upstream analysis into every downstream note either — that bloats notes and duplicates content that's already saved elsewhere; wire a save button onto the upstream stage itself so it becomes its own note, and let §1's `related`/wikilink matching connect the two.

### 3. Retrieval — Graph RAG without embeddings

This is the part worth stealing even if nothing else in this skill gets built. Full algorithm and scoring details are in `references/graph-rag-algorithm.md`; the shape of it:

1. Score every note by keyword overlap against the current query. Take the top ~3 as **seeds**.
2. Build a graph over all notes: an edge for every resolved `[[wikilink]]`, plus an edge between any two notes that share a distinctive quoted/backtick phrase (an "anchor term") — cheap proxy for "these are about the same specific thing" without running an LLM extraction pass over the whole vault.
3. Expand one hop from the seeds via BFS. Neighbors get pulled in at roughly half their connecting seed's score — this is the actual payoff: a note with zero keyword overlap can still surface because it's linked to something that matched.
4. Rank everything, greedily fill a character budget (roughly 2000–2500 chars normal, 800–1000 chars when the conversation is already long and context is tight), and inject it labeled by how it was found — 🎯 for a direct keyword match, 🔗 for a graph neighbor. That label isn't just for the model; showing it to the user makes the retrieval legible instead of a black box.

No vector store, no embedding calls, no network round-trip — it's regex and a keyword scorer walking the filesystem. That's what keeps it fast on modest local hardware, and it's why this approach beats reaching for an embedding pipeline by default: only add embeddings later if keyword+graph retrieval demonstrably misses things it shouldn't.

### 4. Self-RAG — a trust layer on top of retrieval, toggleable

This is a mode switch, not a permanent behavior — some questions genuinely don't need wiki grounding, and forcing it everywhere just makes casual answers slower and more hedged.

When **on**:
- Surface a running `verified.md` — previously self-grounded claims — with the *highest* priority in context, above the raw retrieval results from §3.
- Require every factual claim in the output to carry `[근거: source]` (grounded) or `[추측]` (guess). End the answer with a one-line self-audit: `자가검증: 사실 N개 / 추측 M개`.
- If guesses outnumber grounded claims, the model should refuse to answer substantively and say so — "정보 부족" — rather than produce a confident-sounding answer built mostly on guesses.
- After the response, scan it for `[근거:]`-tagged lines and append those claims to `verified.md`. Next time, those surface first. This is the self-reinforcing part: what got grounded once becomes the trusted baseline for next time, and it accumulates without any manual curation step.

When **off**: the model just answers from its own general knowledge, no tagging required, no wiki lookup forced. Good default for anything that isn't actually about the accumulated knowledge.

**Better default: auto-detect instead of a manual toggle.** A checkbox the user has to remember to flip before every fact-sensitive question adds friction and gets forgotten. Mirror whatever heuristic the project already uses to decide "does this need a live web search" (a keyword list — "정확히", "몇 개", "언제", "결정해야", decision/quantity/date-sensitive phrasing) and auto-enable Self-RAG on that same signal, keeping the manual toggle only as a "force it on for everything" override. Return *why* it turned on (auto vs. user-forced) alongside the response so the UI can show a small "자동으로 검증 모드 적용됨" indicator — the point is the user never has to think about it, but can still see when it fired.

### 7. Multi-context isolation — when one vault serves more than one domain

Skip this section if the assistant only ever serves one audience/context. Add it the moment a second one shows up: a second client, a second channel, a second product line, or even just a second distinct *feature* writing into the same vault (e.g. a chatbot's own notes vs. a separate content-generation feature's notes). Without it, retrieval eventually surfaces a customer-A specific detail while answering about customer B, or a marketing-team note while answering an engineering question — and it gets *worse* over time as more contexts pile into the same flat category structure, not better.

The fix is cheap and doesn't require redesigning storage:
- Add two more frontmatter fields to every note: a **context tag** (which tenant/channel/audience this belongs to, empty string if it's genuinely context-agnostic — general skills/decisions usually are) and a **source tag** (which feature/subsystem produced it, for observability more than filtering).
- These are **caller-supplied, not AI-inferred** — the code path that triggers note creation already knows which tenant/context it's running in, so just pass that value straight through into the note. Don't ask the LLM to guess it; that's a fact the surrounding system already has for free.
- Filter §3's retrieval by the context tag: a note whose context tag is set and doesn't match the current context is excluded from being a seed *or* a graph neighbor — not down-weighted, excluded, because a wrong-context match is worse than no match. A note with an **empty** context tag (genuinely general knowledge) stays eligible regardless of current context — don't over-filter and lose the shared knowledge that's supposed to be shared.
- The source tag can start as metadata-only (tagged at write time, not yet filtered at read time) — decide whether it needs to become a hard retrieval filter later based on whether cross-feature bleed actually turns out to be a problem in practice, rather than guessing upfront. Channel/tenant bleed is usually worth filtering immediately (wrong-customer data is a real incident); cross-feature bleed inside one tenant is often fine or even useful (one feature's grounded knowledge legitimately informing another) and a hard filter there can remove signal you actually wanted.

### 5. The verification gate at *creation* time — the gap this skill fixes

Self-RAG (§4) verifies claims when the model **answers using** stored knowledge. It says nothing about whether the knowledge was accurate **when it was stored**. In the reference implementation, note creation is: AI restructures the raw content → file gets written → git push, gated only on whether the file write succeeded — never on whether the note is actually faithful to the source. A `confidence_score` field exists in the frontmatter, but it's a value the AI is told to write from a template, not something checked against anything.

Left alone, that's a real problem: a note that quietly drifted from its source doesn't just cause one bad answer — §3's graph traversal means it keeps getting pulled into unrelated future context, and §4 can even auto-promote a claim built on it into `verified.md`, where it then outranks everything else. One ungrounded note early on can quietly poison a lot of answers downstream, and it'll look *more* trustworthy over time, not less, since nothing is checking it against the source it supposedly came from.

The fix costs almost nothing if done right: **have the same LLM call from §2 also emit a grounding self-check** — a structured field alongside the note content, e.g. `{ "note": {...}, "grounded": true/false, "issues": ["claim X isn't actually in the source"] }` — rather than firing off a second, separate verification call. One call, one extra field, checked before the note gets saved or pushed; if `grounded` is false, surface the issues and don't commit. This is a few-second, occasional-event cost (only happens when someone deliberately saves to the brain, not on every chat turn), and it's the one piece of this whole design that's non-negotiable if the surrounding project holds itself to a "never let fabricated content pass as verified fact" standard — don't build the rest of this pattern without it.

**Don't stop at "surface the issues and don't commit" — feed them back for one corrective retry.** A `grounded: false` result already tells you exactly what's wrong (the `issues` array). Throwing that away and either giving up or making the user click save again (which re-triggers the identical prompt with zero memory of what failed) wastes the one piece of information you just got for free. Instead: call the same structuring endpoint again, this time passing the previous attempt's content and its `issues` back in as extra context, with an instruction to fix only the flagged parts using content actually present in the source (or drop the unsupported claim entirely rather than keep guessing). Cap it at one retry — if it's still `grounded: false` after that, stop and surface the block; a retry loop just hides the failure instead of showing it. See [[ai-judgment-verification-step]]'s "self-critique-via-schema + one corrective retry" section for the shipped version of this.

**A related but distinct judgment worth adding to the same call: did the source even contain real content?** Everything above covers whether the *note* is faithful to the source — it says nothing about cases where the source itself was worthless (a login wall, an empty listing, a permission-denied page) because ingestion pulled from a gated site without a session. This is common the moment ingestion can fetch URLs: an unauthenticated request to a members-only page often returns HTTP 200 with a real-looking page — just not the page anyone asked for. Add one more field to the same structuring call — `access_blocked: true/false` plus a one-line reason — with an explicit rule: true only when the source is *substantively* just navigation/login/empty-state noise; if there's even one real fact in it, false. When true, skip the corrective retry entirely (there's nothing to correct — retrying against the same worthless source just wastes a call) and surface a distinct message to the user ("this link looks login-gated") instead of the generic grounding-failure message, so a legitimately-thin-but-real note and an actually-blocked fetch don't look the same in the UI.

**This still has a blind spot the LLM judgment can't close on its own**: a site that silently redirects a gated URL to its own public homepage instead of showing an error returns content that's genuinely real (contact info, business hours, a real notice) — so the model correctly says `access_blocked: false`, `grounded: true`, and produces an accurate-but-useless note, because nothing about the text looks like a block from the model's point of view. Found 2026-09-10 in the 루카루카 안경원 CRM's wiki ingestion: a lens vendor's B2B product-catalog link, fetched before login, silently rendered the public homepage instead of erroring; the resulting note was 100% accurate and 100% not what was asked for, and re-testing the exact same raw text against the `access_blocked` prompt confirmed the LLM judgment doesn't catch it — there's no textual signal for it to catch. The fix isn't a smarter prompt — it's a deterministic side-channel check the LLM never needs to reason about: cache one homepage snapshot per domain (fetched once, *separately*, the first time that domain is seen — not derived from whatever URL happened to be requested first, since that first request might itself already be the redirected one), and for every later URL from that domain that isn't the homepage itself, compare its fetched text against the cached snapshot with plain string similarity (e.g. Python's `difflib.SequenceMatcher`). High similarity on a non-homepage URL is close to unambiguous proof of a silent redirect, and the check costs nothing — no LLM call, sub-millisecond, run *before* the structuring call even fires so a caught case skips the expensive call entirely. Verified in production: correctly flagged the redirected content at 100% similarity, and correctly left a real, distinct product page unflagged. **General lesson**: when an LLM verification judgment has a structural blind spot — the content it's judging is honestly real, just not what the caller actually wanted — don't try to prompt-engineer the model into inferring intent it has no way to know; add a cheap deterministic check alongside it that catches that specific failure shape instead.

**A third blind spot, different from the other two: pages that render their real content client-side.** The homepage-redirect case above still has *some* real content in the raw fetch (a redirect target). A worse case is a page whose static HTML is genuinely empty of substance because a plain HTTP fetch never runs the page's JavaScript — what comes back is just the site's navigation shell (menu labels, a login/signup widget, footer links), with the actual body populated only after client-side rendering. Found 2026-09-10 in the same project on a *different* vendor's homepage: the fetched text was a flat list of menu items like "세계최초 뇌과학 렌즈" (a brand's specific-sounding product-line name) — and the structuring model read that as real content and said `access_blocked: false`, because the label itself sounded concrete enough, even though there was no accompanying description, price, or spec for it anywhere in the source. The fix was two-part: (1) sharpen the `access_blocked` rule to explicitly separate a table of contents from body content — "an item name sounding specific and plausible is not the same as the name having any explanation attached to it in the source" — and (2) when a URL still comes back `access_blocked` after that, automatically retry **once** by rendering the page in a real headless browser (Playwright) and re-running the same structuring call on what that produces, before giving up and telling the user the link looks blocked. This is the same "add a corrective retry instead of just failing" shape as the grounding retry above, aimed at a different root cause (JS-dependent content, not a fixable factual error). Verified end-to-end: first pass on the raw fetch correctly flagged `access_blocked`, the browser-rendered retry pulled real content (in this case, footer/contact info the JS-rendered DOM exposed that the static fetch never saw), and the second structuring pass saved successfully — three-layer defense (LLM login-wall judgment → code-level homepage-redirect check → browser-render retry) each catching a failure shape the other two can't.

**A fourth layer, for the block that's real: some sites genuinely require an authenticated session, and no amount of retrying fixes that.** The naive fix — store the vendor's username/password server-side and log in programmatically before every fetch — is a real security liability if done carelessly (plaintext credentials sitting in a config file or database is a classic way to turn "convenient scraping" into "leaked B2B account"), and it's also the wrong tool: what ingestion actually needs is *an authenticated session*, not the credential that produces one. Playwright's `storage_state` (cookies + local storage, saved to/loaded from a JSON file) separates those two things cleanly. The one-time cost is a real login: open a **visible, non-headless** browser window and let the human type their own username/password into it directly — the code never sees, receives, or touches the credential at any point, only what comes after: `context.storage_state(path=...)` captures the resulting cookies once the user confirms they're logged in. Every later fetch for that domain — both the fast `requests`-based path (extract `{cookie.name: cookie.value}` from the saved state and pass it as `requests.get(url, cookies=...)`) and the Playwright browser-render path (`browser.new_context(storage_state=path)`) — reuses that saved session instead of hitting the site cookie-less. This is strictly better than a stored password on every axis that matters here: it expires on its own (sessions time out; a stored password doesn't), it can't be used for anything beyond browsing that one site (no password-reuse blast radius against other systems), and the capture step is a normal human login the user was going to do anyway — nothing new is asked of them except doing it once, in a browser window instead of the site's usual login page, so the result can be saved. Treat the saved session file the way you'd treat any bearer token (gitignored, not committed, not logged) — meaningfully sensitive, but a materially smaller liability than the password that produced it.

**The grounding principle applies to AI-generated references, not just prose claims.** A wikilink, a category, a foreign key into existing data — any field where the model is supposed to point at something that already exists — needs the same "verify before persisting" treatment as a factual claim, and for the same reason: the model can be confidently wrong about a reference exactly as easily as about a fact. Found in the same project: the model's suggested `[[wikilinks]]` frequently near-missed real note titles (a dropped underscore, a rephrased word) — these aren't caught by `grounded`/`issues` at all, since the link *looks* plausible and isn't a factual claim about the source. They silently accumulated as broken links across the vault, invisible until someone actually clicked one. Fixed by filtering suggested wikilinks against the real existing-title set at write time (`wikilinks = [l for l in suggested if l in existing_titles]`), keeping only exact matches instead of trusting the model's string.

### A real bug: parsing "structured knowledge" with a naive "next heading" cutoff silently truncates most notes

Found 2026-09-08 in the 나만의콘텐츠생성기 production build, while chasing a user-reported issue ("does the blog writer actually look up the product I mention?"). The parser that extracts a note's `## 📖 Structured knowledge` body (for §3's retrieval) worked by regex: capture everything between that heading and *the next* `##`-style heading. That's correct only if the structured knowledge itself never contains its own subheadings — but real pasted content (a price catalog, a product spec sheet, anything with more than one paragraph) very often does, exactly like `references/note-schema.md`'s own worked example, which uses `### 1. GUI and CLI setup` / `### 2. OpenAI-compatible local API` *inside* the same section. A naive "stop at the next `##`" regex doesn't distinguish "a subheading that's part of this note's own content" from "the note's next top-level section" — worse, it doesn't even need an exact `##`: any `###`-or-deeper heading also contains a `## ` substring, so it false-triggers on `###` too, not just `##`.

**Real measured impact**: a registered Ray-Ban product-catalog note — full content ~2,000+ characters — was being parsed down to **30 characters** (everything up to and including its own first `## 회사 정보` subheading, then nothing else). Checked the rest of the vault the same day: this wasn't a one-off, multiple notes with any internal subheading structure were silently truncated the same way. Since §3's retrieval is the *only* thing standing between "user mentions a specific product model number" and "the writing model actually sees that model's price/specs," a note truncated to its first paragraph might as well not have the rest of its content at all — and there was no error, no log line, nothing visibly wrong; the feature just quietly returned less than it should have, for as long as the vault existed.

**The fix**: anchor the "where does the structured-knowledge section end" check on the note schema's own *fixed, known* next section markers (`## ⚠️ Contradictions & updates` / `## 🔗 Links`) — not on "any heading-looking thing." Concretely, require the emoji, not just the `##`, right after the newline. This is a direct instance of a broader rule: **when parsing a document with a fixed, known outer structure that wraps free-form inner content, never key the outer-structure boundary off a pattern (any heading) that the inner content is also free to use.** Match on something the inner content provably can't produce by coincidence — a fixed emoji marker, a unique delimiter string, a schema field boundary — not a generic markup pattern like "the next heading."

**A second, related bug found in the same investigation**: even once the section boundary was fixed, §3's "seed match gets a body excerpt too" enhancement (added in an earlier session, not in the original algorithm doc above) was pulling a blind `body[:400]` prefix — the note's own opening paragraph, every time, regardless of what the query was actually looking for. Real case: searching for a specific model ("AVIATOR PUFFER") correctly identified the right note as the top seed, but the model's price sat at character 474 of the body — 74 characters past the cutoff — so the retrieval still returned the wrong slice of the right document. Fixed by finding where the query's keywords actually occur in the body and centering the excerpt window there, with one non-obvious refinement: **take the *furthest* keyword match, not the nearest.** A generic keyword (a brand name, a category word) tends to match trivially near the very start of a note — because it's often literally in the title/opening sentence — while the specific detail someone is actually searching for (a model number, an exact spec) tends to live deeper in the structured content. Centering on the *nearest* match kept re-selecting the useless opening paragraph for exactly the queries this was supposed to fix.

**The general lesson, twice over in one sitting**: a retrieval system can have a fully correct scoring/ranking algorithm (§3's seed+graph-expansion logic worked perfectly here) and still fail completely at the boundary-detection or excerpt-selection layer underneath it — layers that are easy to write once, believe are "just plumbing," and never revisit. When a user reports "it doesn't seem to be using X," don't assume the bug is in the ranking logic; check whether the content the ranking logic is operating on was even extracted correctly in the first place. A `len(extracted_body)` sanity check across the whole vault (here: 30 characters where 2,000+ was expected) would have caught this in seconds — worth running as a periodic health check, not just when a user happens to notice.

### A second real bug: same-title collisions silently overwrite different notes

Found 2026-09-10 in the 루카루카 안경원 CRM, while batch-ingesting a paginated B2B product catalog one link at a time (11 pages of one lens category, submitted link by link across a session). The note filename is a slugified version of the model-generated `title` field — and nothing stops the model from independently picking the *same* title for two calls that are actually different source pages, which is entirely plausible when consecutive pages share a category name and differ only by a page number that rarely makes it into a natural-language title. Writing a note is a plain "open this path and write" — it has no way to tell "this is an intentional re-save of the same thing" apart from "this happens to collide with something unrelated."

**Real measured impact**: a page count taken after the batch (11 pages processed) came up one file short (10 saved instead of 11) with zero errors logged anywhere. Diagnosed by reading the survivor's `source:` frontmatter field, which named only the *last* page's URL — meaning an earlier page had generated the same title, been written first, and then been silently clobbered by a later page's write. A second pass later in the same session found this had actually happened twice (two lost pages, not one), only caught the first time by a manual file-count check that had no reason to be run except suspicion.

**The fix**: before writing, check whether a file already exists at the target slug path. If it does, read *its* `source:` frontmatter and compare against the source being written now. Same source → this is a legitimate re-ingest/refresh of the same thing, overwrite as normal, that's expected and safe. Different source → the filenames collided by coincidence, not by design; disambiguate by appending a short hash of the new source to the slug instead of overwriting, so both notes survive as separate files.

**General lesson**: whenever a filename or id is derived from LLM-generated content — not from something the caller already holds, like a URL, a timestamp, or a database key — the model can coincidentally regenerate the same value for genuinely different inputs, and a plain "write to path" silently treats that coincidence as an intentional overwrite. Guard every LLM-derived-filename write path with an existing-file check keyed on something the caller *does* control (here: the source URL/label), not just on the LLM's own output.

### A third real bug: the structuring model quietly summarizes long repeating lists instead of transcribing them

Found 2026-09-10 in the same project, on a category-listing page with ~200 "product name / price" pairs in the raw source. Nothing in §2's prompt forbade summarizing — rule 4 just said "concrete enough to quote later" — and against a long flat list, the model's default instinct was to compress: it named a handful of items as "examples," bucketed the rest into price ranges ("27~35만원대 다수"), and stopped there. The note that came out was fluent, well-organized, and **not useful** — a customer asking the chatbot about a specific item not named as an "example" would get nothing, even though that item's exact price was sitting right there in the raw source the whole time.

**Real measured impact**: before the fix, a 205-item page produced a note naming roughly 6–8 items by name. After adding an explicit rule ("if the source is a repeating item-list shape, transcribe every item — no ranges, no 'examples: X, Y등'"), the same page produced a note naming 189 of 205 items (92%) — verified by counting price-label occurrences in the raw source against the same count in the model's output, and by checking `finish_reason: "stop"` (not `"length"`) plus completion tokens well under the budget cap, confirming the shortfall was the model occasionally dropping an item rather than being cut off.

**General lesson**: a generic "be specific, don't summarize" instruction is not enough once the source has a *repeating, enumerable* shape (a price list, a spec table, a roster) — models default to compressing long repeated structures into representative examples unless told not to, specifically and by name, for that shape. When the source is shaped like "N repeated records," add a rule naming that shape explicitly and forbidding range/example compression for it; verify the fix by counting a countable marker (an item label, a price occurrence) in the source vs. the output, not by reading the note and judging it "looks thorough." A summarized note reads *more* polished than an exhaustive one, which makes this exact failure mode easy to approve on a skim.

### A fourth real bug: a near-empty homepage isn't always `access_blocked` — it can be a meta-refresh redirect, an iframe/frameset shell, or a mojibake'd encoding

Found 2026-09-11 across two different vendor sites in the same CRM project, both diagnosed as "저장 실패: 원문이 비어 있습니다" (empty source) before reaching the LLM judgment at all. Two distinct root causes, same symptom:

- **Meta-refresh redirect**: `clearway.co.kr`'s root URL was 63 bytes of `<meta http-equiv="refresh" content="0; url=./gbbs_shop/shop/">` and nothing else — a real HTTP redirect (3xx) gets followed automatically by `requests`, but this browser-only redirect mechanism does not, so the fetch "succeeded" with essentially no content.
- **Iframe/frameset shell**: `rgplens.co.kr`'s entire visible site lived inside a same-domain `<iframe src="main/main.html">`, with the outer document itself carrying ~12 characters of text. Fixing meta-refresh alone didn't help here — a different failure shape needs a different check.

**The fix**: one function, `_http_get_following_meta_refresh()`, that loops (capped at a few hops) checking both conditions after every fetch — a `<meta refresh>` tag, or (only if the page's own visible text is under ~100 chars *and* a same-domain `<iframe>`/`<frame>` exists) follow that frame's `src`. Route every fetch call site (content fetching, category-link discovery, and the browser-retry path below) through this one function rather than a raw `requests.get()`, so a fix here automatically covers every caller.

**A third, unrelated cause of the same symptom, found on the same pass**: when a server doesn't declare a charset in its HTTP headers, `requests`' `.text` falls back to guessing (often wrong — `ISO-8859-1`), silently garbling non-ASCII content into mojibake that then reads as meaningless noise to both a human and the LLM judgment. Fix: pass `.content` (raw bytes) to the HTML parser instead of `.text` (already-decoded string) — letting the parser's own encoding detection (which checks `<meta charset>` etc.) do the job correctly, at every fetch call site.

**General lesson**: "empty/near-empty content" from a fetch has at least three structurally different causes that all present identically to an LLM judgment — a genuine access block, a client-side redirect mechanism the fetch library doesn't follow automatically, and a same-domain content wrapper (iframe/frameset) — plus a fourth *adjacent* failure (encoding) that doesn't look empty so much as garbage. Don't let the LLM `access_blocked` judgment absorb all of these; the redirect/iframe/encoding cases are all deterministically detectable and fixable in code, before the content ever reaches a model call, exactly the same reasoning as §5's other deterministic side-channel checks.

### A fifth real bug: a site's navigation menu can have zero `<a>` tags in the static HTML — link *discovery*, not just content fetching, needs a browser-rendered fallback

Found 2026-09-11, same project, `rgplens.co.kr` again but a different pipeline stage: once content-fetching was fixed (above), §9's whole-site category-link discovery still returned 0 candidate links for this site. Direct inspection confirmed the static HTML genuinely contains zero `<a>` tags anywhere in the menu — the entire navigation is injected by JavaScript after page load, the same underlying cause as §5's "third blind spot" for *content*, but this time it broke *link discovery*, a separate code path that had never been routed through a browser-render fallback because it hadn't needed one before.

**The fix**: give `_discover_category_links()` the same shape as the content-fetching fallback — try static-HTML link extraction first (cheap, works for the common case); if it finds zero candidates, render the page via Playwright and re-run the same link-extraction logic against the rendered DOM (`page.content()`) instead. Verified end-to-end: 0 links found statically → 5 correct category links found via the browser-render fallback in ~22s.

**A related wiring bug found while fixing this**: the *existing* `access_blocked` → browser-retry path (for content, not links) was still failing on this same site even after the above fixes, because `_fetch_url_via_browser()` navigated the real headless browser to the **original, unresolved** URL — not the meta-refresh/iframe-resolved real URL from the fix above. The browser could run JS fine, but it was rendering and reading the wrong (outer, ~12-char) document; `page.inner_text("body")` doesn't reach across an iframe boundary into a different document. Fix: have the browser-retry path *also* call `_http_get_following_meta_refresh()` first, exactly like the plain-HTTP path does, before `page.goto()`.

**General lesson**: when a site-shape problem (redirect, iframe, JS-rendering) gets fixed for one pipeline stage (content fetching), audit every *other* stage that independently fetches the same kind of URL (link discovery, a retry/fallback path, anything with its own `requests.get`/`page.goto` call) — the same site-shape edge case tends to exist in each of them independently, and fixing it in one place silently leaves the others still broken until someone happens to test that exact combination.

### A sixth real bug: an output token budget sized for short answers silently truncates once a different rule demands long ones

Found 2026-09-11, same project, on a large price-list PDF upload that failed with "모델 응답에서 JSON을 찾지 못함" (JSON not found in model response) — a confusing error, since a JSON object clearly *had* started in the raw output. Root cause: an earlier rule (§"A third real bug" above — transcribe every item in a repeating list, don't summarize) was doing exactly what it was supposed to on a long list, which meant the model's *actual* output length grew well past `max_tokens` (16000, sized months earlier for typical short answers), cutting the response off mid-object before its closing braces — a `finish_reason: "length"` truncation, not a genuine missing-JSON failure, but the two produce an identical-looking symptom ("no valid JSON found") to whatever code just does `json.loads()` and catches the exception.

**The fix, two parts**: (1) check the model's real context window via its serving API (LM Studio's `/api/v0/models` extended endpoint exposes this) rather than guessing — it was 262,144 tokens here, vastly larger than the 16000-token output cap that had never been revisited since being set for a different, shorter-output use case — and raise `max_tokens` accordingly (48000). (2) Distinguish the two failure shapes in the error message itself: check `finish_reason == "length"` before assuming "no JSON found" means the model produced garbage; a truncation and a genuine parse failure need different user-facing messages and different fixes.

**General lesson, and it compounds with §"A third real bug"**: a rule that legitimately makes output longer (transcribe-everything, don't-summarize) and a token budget sized before that rule existed are two settings that can silently drift out of sync — the rule doesn't fail loudly, it just eventually collides with a cap nobody thought to revisit. Whenever a "be more thorough/complete" instruction is added or strengthened, re-check whether the output budget it now has to fit inside is still generous enough, the same way §"What not to do" already warns about re-checking `max_tokens` after swapping *models* — the lesson generalizes to after strengthening *instructions*, too.

### A seventh real bug: raw-text extraction can silently truncate a document before chunking ever gets a chance to run

Found 2026-09-11, same project, on the exact same large PDF that triggered §"A sixth real bug" — fixing the output token budget didn't fix the underlying complaint ("자료 다 지식화 했는데 왜 모르지" / "I gave you everything, why doesn't it know"). The real cause was one layer earlier and completely different: `extract_pdf_text()`'s raw-text extraction step had its own independent `max_chars=24000` cap, applied via a flat `text[:max_chars]` slice *before* the text ever reached chunking. The real file was 56 pages / 272,496 characters; the cap kept only the first ~6 pages. Two specific product models the user asked about (a "Zaya" sunglasses SKU and model "RB4456F") both sat around character 115,700 of the real extracted text — nowhere close to surviving a 24,000-character cut. Confirmed directly against the user's real file: `len(extracted_text)` was 24,000 both before and after the earlier `max_tokens` fix, and only dropped the truncation once this separate cap was found and raised.

**Why this was easy to miss even after fixing the adjacent bug**: §"A sixth real bug"'s fix (raising `max_tokens` from 16000 to 48000) is a real, necessary fix for a real, separate failure mode (the model's *output* getting cut off mid-JSON) — but it operates several steps downstream of extraction, and fixing it produces no error and no obvious symptom that the *input* was already wrong. The two bugs share a parent cause (a cap sized for a smaller, older use case never revisited) and a similar-sounding symptom ("this large document isn't fully processed"), which makes it tempting to declare victory after fixing the first one found — always re-verify the user's original complaint against the *actual*, currently-running code end-to-end, not just confirm that the specific error message they showed you is gone.

**The fix**: raised `extract_pdf_text`/`extract_docx_text`/`extract_xlsx_text`'s default `max_chars` from 24000 to 1,000,000 — matching the same "safety valve against a pathological input, not a real limit for realistic use" reasoning `fetch_url_text()` already used for its own 100,000-char cap. Downstream chunking (`_split_chunks`) already exists specifically to split a long document into LLM-sized pieces safely, so the extraction step's only job is to not throw away real content before chunking gets a chance to run on it.

**General lesson**: a pipeline with N sequential stages can have the *same class* of bug (an unrevisited size cap sized for an old, smaller use case) at more than one stage independently, each one capable of fully explaining the user's symptom on its own. Fixing the most-downstream one you find first (usually the one with the clearest error message) doesn't mean the upstream ones are fine — trace the *data*, not just the error message: check the actual byte/character count surviving each stage against a real large input, end to end, before declaring a "your document is too big" complaint resolved.

### An eighth real bug: naive character-offset chunking splits individual records across a chunk boundary

Found 2026-09-11, same project, once the extraction cap above was fixed and the same real Ray-Ban catalog was fully re-processed. `_split_chunks()` sliced the raw text at a flat character offset (`text[i:i+size]`) with zero regard for where a line happened to fall — harmless for prose, but this document (like most price lists) has one full product record per line (model/color/size/price all on one line). Checked directly against the real 272,496-character file: **all 13 chunk boundaries** under the old 20,000-character chunking fell mid-line, e.g. cutting `...레이밴 0RB2341 1354M3 51 157,124 350` from `,000 ROUND METAL Black | Ultra Black...` — that product's price data split into two separate chunks, each seeing only half the line, each getting sent to the model as if it were a complete, standalone input.

**The fix**: back up the chunk boundary to the nearest preceding newline whenever it would otherwise land mid-line, so a chunk only ever ends mid-line when a single line is itself longer than the chunk size (an edge case handled by falling back to a hard cut, since there's genuinely no better option there). This trims each chunk slightly under the target size rather than exactly to it, which is the right trade — a chunk a few hundred characters smaller costs nothing; a chunk that silently corrupts the one record sitting on its boundary costs real data. Verified with a targeted test: a 32,000-character synthetic file of 700 one-line records, chunked at size=500, produced zero mid-line cuts and reassembled byte-for-byte identical to the input.

**A related, softer optimization from the same investigation**: chunk size interacts with total processing time in a way that's easy to misjudge. Doubling the chunk size roughly halves the number of LLM calls (and the fixed per-call overhead — re-sending the structuring instructions, re-processing the existing-note-titles list), but it does **not** meaningfully reduce total generation time, because a "transcribe every item, don't summarize" rule (§"A third real bug") means total *output* content scales with how much real content there is, not with how it's sliced — the same total number of product rows still has to be typed out by the model regardless of chunk boundaries. A real 56-page catalog took roughly an hour end-to-end even after this and the token-budget fix, running on a small local model (`google/gemma-4-e4b`) — that's the honest floor for "fully, faithfully transcribe a genuinely large document with a local model," not a bug to keep chasing. Don't oversell chunk-size tuning as a fix for that; it trims overhead, not the real work.

**Companion UX fix, same investigation**: a multi-chunk job that can now legitimately take many minutes had no way to show progress — a single blocking request/response, so the frontend could only show a static spinner for the whole duration, which reads as "is this stuck?" for anything longer than a minute or two. Added a client-generated `job_id` threaded through the ingestion call chain, updated in a small in-memory `{job_id: {total, done, current}}` dict after each chunk completes, polled by the frontend every ~1.5s via a dedicated GET endpoint to render real "N/M chunks processed" text. Scoped deliberately to the single-call-produces-many-chunks case (one large file/URL) rather than every ingestion path — a multi-URL loop or whole-site crawl already has its own per-item progress from the loop itself in the calling code, so adding a second, overlapping progress mechanism there would be redundant, not additive.

### A ninth real bug: deduplicating link candidates by visible text instead of destination URL can silently drop a real category

Found 2026-09-11, same project, while chasing a user-reported gap: a chatbot query for a specific product model ("rr005") came back unknown, even though the model's product page was reachable from the vendor site's homepage. The site (rimrockeyewear.com, a Cafe24-platform shop — a very common Korean small-shop e-commerce SaaS, likely to recur across this project's other vendor sites) has two genuinely different category pages whose static-HTML link text is **identical**: both render as "SHOP NOW", one linking to `cate_no=29` (a different, unrelated category) and the other to `cate_no=31` ("Rimrock Retro" — the exact category containing every RR-prefixed model, including the one asked about). `_extract_link_candidates()` deduplicated the page's links keyed by visible text (`seen.setdefault(text, url)`), so the second "SHOP NOW" link — a completely different destination — was silently discarded before it ever became a candidate. No classification-prompt fix could have recovered it, because it never reached the classifier at all; §9's own earlier-documented "don't rely solely on the classification prompt — pre-filter first" principle applies here too, but one layer earlier than that section describes: pre-filtering isn't only about excluding junk before the LLM sees it, deduplication logic itself can just as easily discard something real before the LLM ever gets a vote.

**The fix**: dedupe by normalized destination URL instead of by link text — legitimate reason to dedupe at all (the same URL reachable via a logo image and a text link shouldn't appear twice) still holds, it just needs the right key.

**Two more issues found and fixed in the same pass, both compounding the same underlying "the real category never reached the classifier" shape**: (1) individual product-detail page URLs (Cafe24's `/product/<slug>-<id>/category/<n>/display/<n>/` shape) were leaking into the candidate pool and occasionally getting *misclassified as categories* by the LLM — filtered out deterministically by URL-shape before the candidate ever reaches the prompt. (2) The classification prompt's own "애매하면 포함하지 마세요" (if ambiguous, don't include) instruction, entirely reasonable in general, correctly-per-instruction excluded a bare brand/collection name ("Rimrock Retro") that reads as ambiguous in isolation but is a completely real, distinct product category for a single-brand eyewear shop. Rather than trying to prompt-engineer around this (any wording loose enough to include "Rimrock Retro" risks also including genuine brand-story links), added a second deterministic override in the other direction: Cafe24's category-*listing*-page URL shape (`/product/list.html?cate_no=N`) is reliable enough on its own to auto-include a candidate regardless of what the LLM decided — the same "deterministic side-channel check beats LLM judgment where a reliable mechanical signal exists" principle as §5, just applied to link classification instead of content grounding.

**General lesson, tying all three together**: when link/category discovery for a specific real site produces a wrong result, don't assume the bug is in the LLM classification step just because that's the visible decision point — by the time a candidate reaches the classifier, it has already survived extraction, deduplication, and pre-filtering, and a bug in any of those earlier stages can make a real category structurally unable to be chosen no matter how the prompt is worded. Verified end-to-end against the real site after all three fixes: discovery returned exactly the 4 real product categories with zero false positives, versus the original run that silently dropped 2 of them and included 2 non-category pages.

### 8. Automatic pagination discovery — one link can actually be many pages

A category/listing page frequently shows only a slice of what it links to — "8 best-sellers" on a homepage when the real catalog behind it has 500+ items across several listing pages, or one page of a paginated product list whose total count is shown right on the page (`TOTAL / 532`) but whose remaining pages were never fetched. Found 2026-09-10: a homepage ingestion produced an accurate but tiny note (a handful of "best model" teasers) with an explicit "전체상품목록 바로가기" (see full list) link sitting unfollowed in the same raw text — the ingestion had faithfully captured 100% of a page that was itself only 2% of the real content.

**This is not a case for more AI judgment — it's a missing deterministic crawl step.** Given a listing URL, whether it has more pages and how many is answerable by parsing the page itself (a shown total count, or — more robustly — the page's own pagination links), with zero model involvement. Detection approach: compare every same-path link on the page against the current URL: find query-string links that differ from the current URL in **exactly one parameter**, and **filter to links whose visible text is itself a page number** (or a "next"/"이전" label) — not just "any same-path link with one differing param." The unfiltered version has a sharp false-positive mode: a link to a *sibling category* (different content entirely) on the same platform typically differs from the current URL by exactly one query parameter too (the category id), and gets misidentified as "page 31" of the current listing. The text-content filter (pagination links show the page number as their own clickable text; category-switcher links show a category/brand name) is what tells them apart. Once the true pagination parameter and page count are known, generate every page's URL directly (`param=2`, `param=3`, ...) and feed each one through the *existing* single-page ingestion pipeline unchanged — chunking, grounding, access-blocked detection, the browser-render retry, and the slug-collision guard all already handle "one more page of content" correctly, so this feature is almost entirely glue code around capabilities that already exist. Cap the page count (here: 30) as a safety valve against a pathologically large listing. Verified against a real 532-item, 3-page category: correct page count detected, all 3 pages fetched and saved with distinct notes.

**General lesson, paired with the previous one**: "give it one link and trust it to explore" repeatedly turns out to have two very different failure modes that look similar from the outside but need opposite fixes — a page whose *visible content itself* is incomplete (needs an AI judgment call: is there real substance here or not) vs. a page that's *one of several* and the rest were never requested (needs no AI judgment at all: parse the count, generate the URLs, walk them). Diagnose which one you're looking at before reaching for either fix — trying to solve the second with a smarter access_blocked prompt, or the first with a URL-enumeration loop, won't work.

### 9. Whole-site auto-crawl — "one link, knowledge-ify the whole site" without agentic browsing

The natural next ask once pagination auto-discovery works: "why do I still have to give you each category's link — can't you just take the homepage and figure out the rest yourself?" That sounds like it needs the exact agentic-browsing capability this skill already argues local models can't do reliably (§"What not to do": don't extend the structuring model into agentic browsing). It doesn't. The confusion is conflating two different problems: *deciding what to click next by looking at a rendered page* (genuinely needs slow, unreliable visual judgment) vs. *figuring out which of a page's already-parsed links point to real content sections* (a link-list classification problem, not a browsing problem). The homepage's `<a>` tags and their visible text are sitting right there in the fetched HTML — no navigation, no clicking, no multi-step recovery from a wrong click. That reframing is what makes "crawl the whole site from one link" tractable for a small local model where "browse the site like a human" was not.

Concretely: fetch the seed page once, collect same-domain link texts, and ask the model to classify that *list of short labels* — not a full page — against "does this look like a product/content category." That's a tiny prompt (a numbered list of a few dozen short strings in, a few array indices out) instead of a full-page structuring call, so it runs in ~15–20s where a structuring call on the same model took 200–280s: the cost profile of "classify N short labels" and "deeply structure one long page" are not the same task even though both go through the same LLM. Then feed every accepted link through the *existing* single-URL ingestion pipeline (pagination-following, access-block detection, session reuse, slug-collision guard — all already built, all already correct per-page) and merge the results the same way the pagination feature already does. The whole feature is: one cheap classification call, plus a loop around a pipeline that already exists.

**Don't rely solely on the classification prompt's exclusion instructions — pre-filter first.** Even with explicit instructions to exclude login/cart/account/legal/policy links, the model let some through anyway in testing (a company-info page kept getting picked despite "회사소개" being named as an explicit exclusion). Fix: apply a plain keyword blocklist against the link text *before* the link ever reaches the LLM prompt (로그인, 회원가입, 장바구니, 마이페이지, 공지사항, FAQ, 이용약관, 개인정보, 쇼룸/showroom, 게시판, and their English equivalents) — this both shrinks what the model has to classify and catches the exact case the model's own instruction-following didn't. Also strip pure same-page anchor links (`#section`) by comparing the link's path+query with the fragment removed against the current page's, not by comparing full URL strings — an anchor-only link differs from the seed URL only by its fragment, and a naive string comparison won't catch that, so it slips through as a "different page" and gets crawled as if it were new content when it's just the homepage again.

A residual false positive (a company-info or about page correctly classified as *not obviously junk* but not really a product category either) is a low-cost failure, not a dangerous one — the existing per-page pipeline still produces an accurate, grounded note from it, just a less useful one. That asymmetry (a missed real category costs actual coverage; an extra low-value page costs a few seconds and one harmless note) is why the classification prompt should say "if unsure, don't include it" — false negatives here are cheap for the user to notice and fix by hand (paste one more link), false positives are easy to overlook and just add noise.

### 10. Self-upgrade / domain-score memory — reinforcement-style *operational* memory, separate from wiki content

This is a different axis from everything above: §1–§9 are all about *content* memory ("what do we know about this site/product"). This section is about *operational* memory — "did trying to ingest this domain work last time, and if not, why" — the distinction [[self-improving-agent-strategy-memory]] covers in depth; this is that skill's guidance made concrete for this specific pipeline. Don't build a second retrieval system for it — it extends the same vault, just a different, code-only category that's deliberately excluded from chatbot-facing retrieval (see below).

Built 2026-09-11 in the 루카루카 안경원 CRM in direct response to the user asking whether a small local model could "self-upgrade" by scoring its own successes/failures, reinforcement-learning-style. The honest answer (per [[self-improving-agent-strategy-memory]]'s core distinction) is that a small local model can't *discover* a fix to a novel failure on its own — but it absolutely can *record* a structured outcome and *look one up* before retrying, and that's what got built:

- **`domain_scores.json`** (one file, one entry per domain): `{score, success_count, fail_count, history[]}`, updated by a single `record_domain_outcome(domain, success, failure_type=None, detail=None)` call wired into every exit path of `ingest_url()` (success, `access_blocked`, and any other grounding/fetch failure). `score` is just `+1`/`-1` per outcome — deliberately the simplest possible signal, not a tuned reward function; the point is a fast, cheap, mechanically-checkable number, not a sophisticated RL scheme a small model or plain code can actually act on reliably.
- **A per-domain strategy note** (`10_Wiki/Strategies/{domain}_전략_기록.md`) gets appended to — not overwritten — on every *failure*, with a timestamp and the failure type/detail. This is the human/future-agent-readable half: a running "here's what went wrong with this domain and when" log, in the same note-with-frontmatter shape as every other wiki note, so a person (or a future, stronger-model session) can read it directly in Obsidian without needing the JSON.
- **Deliberately excluded from `CATEGORIES`** (and therefore from §3's search/graph retrieval, `build_graph()`, and `_existing_note_titles()`) — these are operational records about the *pipeline's own behavior*, not knowledge content a chatbot should ever surface to an end user asking about products. Keeping the two in the same vault (same repo, same git-sync mechanism) but in a structurally separate, non-retrieved folder is what "extend the existing vault, don't build a parallel system" means in practice.
- **Surfaced in the UI before the user re-attempts something**: the wiki-add form looks up the target domain's score (a tiny GET endpoint, debounced on URL input) and shows a plain green/amber hint — "succeeded N times before" or "failed N times before, may need a login session" — *before* the user submits, not after a failure. This closes the loop [[self-improving-agent-strategy-memory]] describes as step 1 ("query strategy memory before attempting") in the one place a human is actually in the loop making the attempt.

**A same-day follow-on that closes the loop tighter: remember *how* it worked, not just *whether* it worked.** The `score`/`history` above answer "did this domain succeed" but not "what actually fixed it" — so even a domain with three logged `access_blocked` failures still made `ingest_url()` retry the doomed plain-HTTP fetch first, every single time, before falling through to the browser-render retry that was the thing that actually worked last time. Added a `strategy` dict to the same domain entry (`{needs_browser_render, needs_login}`), set from real observed outcomes only — never guessed: the existing browser-retry path already knows, after the fact, whether the browser-rendered attempt is what succeeded (→ `needs_browser_render: true`) or whether the site stayed blocked *even after* real JS execution (→ the JS-rendering fix didn't help, so this is very likely a genuine login wall → `needs_login: true`). `ingest_url()` then checks this *before* fetching: a domain already flagged `needs_browser_render` skips straight to the browser-rendered fetch, falling back to the normal static-first flow only if that produces nothing (in case the site genuinely changed). This is the same "reuse a known strategy is cheap, discovering a new one is expensive" split from [[self-improving-agent-strategy-memory]], just one layer more specific — the *outcome* memory said "this will probably fail," the *strategy* memory says "and here's specifically what to do about it instead of finding out from scratch again."

**Also added: a dedicated "health dashboard" page and a one-click path from a bad score straight into the fix.** A JSON file nobody looks at doesn't actually change behavior — so `wiki-health.html` lists every attempted domain worst-score-first with its success/fail counts, strategy tags, and most recent failure detail, matching this skill's own repeated emphasis (§6, the graph view) that accumulated state needs a legible surface, not just a working backend. For a domain flagged `needs_login`, its card carries a button that deep-links back into the main app (`index.html?startLogin=<domain>`) and — since the user already made the affirmative click on the dashboard — auto-opens the wiki-add modal, pre-fills the login-session URL field, and starts the existing login-session flow immediately, collapsing "I noticed this site keeps failing" → "let me go log into it" from a multi-step hunt into one click. A manual "reset strategy" action is also exposed per-domain (clears just the `strategy` dict, keeps the score/history) for the case a site's underlying structure actually changed and the old strategy no longer applies — sticky-by-default memory still needs an escape hatch for when the world moves out from under it.
- **This is also what makes an existing informal pattern queryable instead of merely readable**: every bug fix in this project already got two write-ups — a detailed git commit message, and a "real bug" section in this very skill file — but neither is something code can look up automatically before acting; both required a human (or Claude) to go read prose. `domain_scores.json` is the same underlying loop (try → observe outcome → remember it → consult it next time) implemented as a structured, `get_domain_score(domain)`-queryable file instead of prose — the two aren't in tension, they serve different consumers: prose (commit messages, this skill) is for a human or a future Claude session designing a fix; the JSON is for the running pipeline's own code, checked on every attempt without anyone needing to read anything.

**What this is not**: it is not the model "learning" in any weights-updating sense, and it doesn't make the local model smarter at handling a *novel* site shape it's never seen — that discovery step still has to come from a stronger model or a person, exactly as [[self-improving-agent-strategy-memory]] argues. What it closes is the *cheaper* half of the loop: never blindly re-attempting a domain that's already shown a pattern of failing, and giving the human a heads-up instead of silent repeated failures with no memory across sessions.

### 6. Sync + visualization — durability and legibility

**Git sync**: after any note is created or edited, `git add . && git commit && git pull (prefer local on conflict) && git push` against a dedicated repo for the vault — separate from the app's own code repo. This is what makes the brain survive a dead laptop; it also means the vault is just plain markdown files that can be opened directly in Obsidian or any editor, not something locked inside the app.

**Visualization** (optional, do it last): render notes as nodes and wikilinks as edges with a force-directed graph library (e.g. `force-graph`, a small canvas/WebGL JS library with no server dependency) — an Obsidian-graph-view equivalent. Nice for the user to see what the system actually knows; not load-bearing for the retrieval to work.

## Adapting to the target stack

None of the above is tied to any particular language or framework — the reference implementation is a TypeScript VS Code extension, but the pattern has been applied to a Python/FastAPI + vanilla-JS app just as well. Concretely translate:
- "00_Raw / 10_Wiki folders" → wherever the target app keeps its local data (e.g. `data/brain/...`)
- "one LLM call with structured output" → whatever structured-output mechanism the target stack's LLM client supports (JSON schema, function calling, or careful prompting + parsing if neither is available)
- "git sync" → shell out to `git`, same commands, any OS
- Keep the note schema (frontmatter fields, section headers) identical across projects even when the surrounding code differs — that consistency is what lets notes from different projects stay legible to each other and to Obsidian.

## 11. Answer-time honesty and style — a different axis from ingestion-time grounding

Everything above (§5, §10) is about making sure a *note* is trustworthy before it's saved. None of it guarantees the *chat answer* that later reads that note stays honest — that turned out to need its own, separate defenses, found 2026-09-11/12 in the same CRM project from real user-reported chat transcripts.

**A tenth real bug: cross-note misattribution — a real fact from the wrong source, presented with full confidence.** A user repeatedly asked a chatbot "what progressive-lens models does brand X sell," got vague dodges, then — under conversational pressure to give *some* concrete answer — the model produced a full table of specific product names. Checked directly: those names were real, but belonged to a *completely different* vendor's note in the same wiki, not brand X's. This is a different failure shape than plain fabrication (§ earlier real bugs): the model isn't inventing a string from nothing, it's cross-contaminating a genuine fact from one retrieved/seen document into the wrong document's answer — and a self-tagging honesty instruction ("don't state what's not in your sources") doesn't reliably catch it, because the model isn't lying about *whether* it has a source, it's wrong about *which* source. The fix is the same shape as §5's ingestion-time grounding check, just moved to answer time: a second, independent, low-temperature LLM call (mirroring a clinical-note cross-check pattern already in production in the same app) given *only this question's actual retrieved excerpt* (not the whole wiki) plus the draft answer, instructed explicitly that "this name is real, I've seen it somewhere" is not sufficient grounding — it must be in the specific excerpt handed to it for *this* question. Verified live: before the fix, a real-but-wrong-brand product list; after, the model correctly cited the real model names that *do* belong to the asked-about brand and admitted the specific requested list wasn't in its materials.

**An eleventh real bug (well, three related upgrades, all from the same "make it feel like talking to Claude" request): retrieval that's too shallow, no way to ask for more, and one-shot comparison scoring.** Three gaps found together while chasing a "I want this chatbot to compare things across brands and reason like Claude" request: (1) the existing keyword-search excerpt (~400 chars) is sometimes just not enough — added a `<read_wiki>note_id</read_wiki>` tag the model can emit, which triggers fetching that note's *full* body and one non-streaming follow-up answer (a small, scoped version of an "agentic pull-based retrieval" pattern seen in a comparable production project — the model decides what to read next instead of the server guessing once and stopping). **Real bug found testing this**: the model emitted *two* `<read_wiki>` tags in one answer; code that only handled the first regex match left the second tag's raw text visible in the final answer shown to the user. Fixed by collecting all distinct requested IDs (deduped) and resolving them together, *plus* an unconditional final regex strip of any remaining `<read_wiki>...</read_wiki>` tags before display, regardless of how resolution went — a **general lesson**: when parsing model output for one instance of a repeatable tag, always assume the model may emit more than one, and always add an unconditional safety-net strip at the end rather than relying on every branch to clean up after itself. (2) A single pooled keyword search across a multi-brand comparison question can let one brand's larger/more numerous notes crowd out another's (the same shape as the IDF-scoring bug below, one level up) — fixed with a cheap, temperature-0 classification call that detects "is this comparing N things" and extracts the entities, then runs the search once per entity so each one gets guaranteed excerpt space, instead of one ranked pool where a bigger note can starve a smaller one.

**A twelfth real bug, and the most conceptually interesting: fixing a "too rigid" complaint by adding more rules made it worse, not better.** The same chatbot kept forcing markdown tables into answers that didn't need one (two lists that fit in three lines each got wrapped in two separate tables) — the user's own complaint was specifically that force-fitting structure "when it doesn't need it" both feels unnatural *and* is a real correctness risk, since a small model formatting a markdown table competently is itself unreliable (wrong column counts, broken separator rows). The instinctive fix — strengthen the existing "use a table only when needed" instruction — was tried the day before and didn't stick. Two research steps, not guesses, found the actual fix: (a) directly reading a comparable reference project's real system prompt (already available locally from an earlier analysis pass) showed it had **zero** formatting/style instructions at all — only tool-call mechanics — and that project's output was independently reported by the same user as feeling more natural/Claude-like than this one's; (b) a 2025 paper on prompt defects (arXiv:2509.14404) found that per-rule instruction adherence measurably degrades as the *total number of rules* in a system prompt grows. Combining both: the previous day's fix had made the problem worse by *adding* a rule to an already rule-dense prompt instead of reducing total rule count. The actual fix was to delete most of a 9-item, ~19-line formatting-rules section down to a few lines with two concrete numeric thresholds (a table needs 3+ items with 2+ attributes each; a step-by-step badge needs an actual real procedure) and keep only the one truly load-bearing bit of syntax in full detail (a `[CHART:...]` tag the frontend actually parses into a real chart — confirmed the decorative bits like callout-boxes and step-badges degrade gracefully to plain markdown if unused, so cutting their instructions couldn't break rendering). Verified live with the exact same query that produced two needless tables before: same local model, zero tables afterward, same facts fully intact.

**General lesson across all three**: when a small/local model's output has a problem that "add a stronger instruction" doesn't fix, consider that the fix might be **fewer instructions, not a stronger one** — a system prompt is a shared resource the model has to divide attention across, and stacking correctness-critical rules (grounding, honesty) on top of style-preference rules (formatting menus) makes both compete for the same limited instruction-following budget. Keep correctness rules (don't fabricate, don't misattribute) even at prompt-length cost — those are worth it — but treat elaborate stylistic menus as the first thing to cut when a prompt is fighting its own model's natural tendencies instead of working with them.

## 12. Domain-scoped retrieval — separating multiple *knowledge categories* within one tenant, not just multiple tenants

§7 covers isolating one vault across multiple *tenants/channels*. A related but distinct need showed up once the same CRM's wiki grew past pure product data: multiple *categories of knowledge* sharing one tenant — brand-specific product specs, general professional knowledge, and business/marketing strategy — that must not bleed into each other even though they're all "the shop's own knowledge." The mechanism is the same shape as §7 (a frontmatter tag, filtered at retrieval, assigned at write time) but the axis is different (domain of knowledge, not audience), and it surfaced its own distinct bugs worth recording separately.

**Real failure motivating this**: a customer asked about a specific brand's progressive lenses; under pressure the model produced a full price table of a completely different brand's real products — not fabricated (a repeat of §11's tenth bug, cross-note misattribution), but *reachable* in the first place because one pooled keyword search over the whole vault treated a general-knowledge note and a competing brand's product note as equally valid matches for the same query. Domain tagging doesn't replace answer-time verification (§11) — it removes an entire class of the *mixing that verification then has to catch*, upstream of it.

**The tag, and how it's assigned**: add a `domain` field alongside `category`, decided by the *same* structuring LLM call from §2 (no extra round-trip) — one value for content specific to one company/brand's product, another for brand-agnostic professional knowledge. A third case — marketing/business content — doesn't get a domain value at all; it gets its own category folder (below).

**Retrieval-time filter, and the one non-obvious rule**: when a domain is specified, exclude any note whose own tag is set and differs — but notes with **no tag at all** (everything ingested before the feature existed) stay eligible regardless of the requested domain. Excluding untagged legacy content by default would silently make an entire vault's pre-existing knowledge invisible the moment filtering ships; the backward-compatible default is "untagged = universal," not "untagged = excluded."

**A fourth category that should never reach domain-filtered retrieval at all**: marketing/business-strategy notes (seasonal promotions, retention tactics) aren't wrong for either domain above — they're a different *kind* of question entirely (how the shop operates, not what to tell a customer), and the failure mode isn't "wrong brand," it's "a customer-facing answer citing an internal promotion memo." Rather than adding a third domain value to the same filtered pool, this content gets its own category folder that the customer-facing search function's code *never iterates over at all* (`notes = [n for n in notes if not n["id"].startswith("Strategies/")]`) — not a tag check a mistagged note could slip past. A second, dedicated read function is the only way to reach it. This is a stronger guarantee than tag-filtering: reserve it for content where the mixing failure would be worse than "wrong but plausible."

**A real bug found migrating existing content to this scheme**: the retry prompt used when a note fails its grounding check (§5) has its own field list for what to re-emit, separately maintained from the main structuring prompt's field list — and it didn't get updated when `domain` was added, so a note that failed grounding on its first pass and needed a corrective retry could silently lose its domain tag on the *second* pass even though the first pass assigned one correctly. **General lesson**: when two prompts in the same pipeline are meant to produce the same schema (an initial pass and its own retry pass), a schema change has to be applied to both — check that every prompt claiming "same format as before" actually has a current field list, rather than assuming that instruction stays in sync with the schema automatically.

**A second real bug, structural rather than a missed edit**: classification is itself a judgment call the same LLM call has to make about content it just produced — exactly the shape that benefits from the "second independent call catches what the first missed" pattern already used for §11's misattribution fix, not a one-shot decision trusted at face value. Added a second, low-temperature call shown *only* the raw source text and the just-assigned category/domain, asked to judge the assignment from scratch — not to review the first call's reasoning, just given the same inputs an independent judge would have. Verified directly: a deliberately mislabeled product price-list (tagged as general knowledge) was caught and reassigned; a genuinely correct classification was left untouched on the same test (no flip-flopping on things already right).

**Backfilling existing content**: rolling this out to a vault that predates the feature means re-classifying every existing note once. Skip already-tagged notes so the backfill is safe to interrupt and re-run without re-spending an LLM call on notes already done — the same "check what already exists before writing" instinct as the same-title-collision bug above, applied to a bulk migration instead of a single write. Run against a real vault (106 notes, one call each): 0 failures, and the resulting split matched manual judgment on the genuinely ambiguous cases (a "how to insert this lens type" note landed as general knowledge; a "this brand's manufacturing process" note about the same lens family landed as product-specific — correctly split on the axis that actually mattered).

## 13. A lead + specialist "team" mode on top of the same wiki — for deep, multi-domain questions, not every-message chat

Everything above serves the ordinary one-shot chat turn. A different, less frequent need showed up once domain separation existed: a question genuinely too broad for one call to answer well — "should we push brand A or B, and what's the marketing angle" touches customer data, product specs, professional knowledge, *and* business strategy at once. Building this as "one call with a bigger prompt" would just recreate the exact cross-domain bleeding §12 exists to prevent. The fix isn't a bigger single call — it's a small number of narrower calls, each genuinely restricted to one domain's data, synthesized by a final call that never touched raw domain data directly.

**Architecture, deliberately not a full agent framework**: one "lead" call reads the free-form question and decides which domain specialists are actually relevant, writing each a narrowed sub-question rather than forwarding the original verbatim. Each dispatched specialist then runs with *only* its own domain's retrieved context — no shared context window, no persona instruction pretending to "forget" other domains, actual data-level exclusion via the same mechanism §12 already provides. This is the load-bearing decision: isolation comes from what data a call is given, never from asking a model to roleplay restraint over data it can already see.

**A real, reproduced failure the lead's free-form task-writing introduced, that domain-scoped retrieval alone doesn't prevent**: the lead occasionally rewrote a brand name into an invented transliteration when drafting a specialist's sub-question, silently breaking that specialist's own keyword search — the wiki is stored in the original language, and a misspelled query matches nothing. Domain-scoped search worked exactly as designed; it just never received the right term. **Fix, two layers**: (1) always include the user's original, unedited question text in every specialist's search query alongside the lead's rewrite, so the source spelling survives even when the rewrite mangles it; (2) don't trust the lead's dispatch judgment alone either — an already-validated entity-detection classifier (the same one behind multi-entity comparison search) runs in parallel with the lead's decision, and if it detects two-or-more specific product names but the lead didn't dispatch the product specialist, force-add it. Two independent signals catching the same class of omission — the "don't trust one judgment call for something a cheap second check can catch" instinct running through this whole skill, applied to *dispatch* instead of content grounding.

**A second real failure, found by reading a specialist's actual output rather than trusting the pipeline ran without errors**: cross-review is supposed to let a specialist fill a gap using another specialist's material — but a specialist whose own domain genuinely lacked data kept repeating "no data available" even after being shown another specialist's answer that, read carefully, already contained everything needed to answer the question in that specialist's own voice. Its grounding rule ("don't answer past your domain's data") was correctly conservative for its own retrieval, but over-applied to the one step whose entire purpose is closing that exact gap. **Fix**: an instruction added only to the cross-review prompt (not the first-pass prompt, where the conservative rule is still correct): if your own answer was a data-gap refusal and another specialist's result actually answers the question, don't repeat the refusal — build a real answer from their material in your own voice, tagged as sourced from another specialist. Verified live, same question before and after: before, the specialist's refusal stood unchanged through cross-review while the *lead's final synthesis* quietly did the connecting work instead (a working final report, but from the wrong layer); after, the specialist's own cross-reviewed answer contained the synthesis, with a visible comment naming what it took from the other specialist and why.

**Bounded to exactly one review round, backed by evidence rather than intuition**: the obvious next question — why not let specialists go back and forth until they converge — is a real, actively studied idea (multi-agent debate; frameworks like AutoGen model exactly this as structured multi-turn dialogue, and CrewAI's role-based crews explicitly support local models via Ollama/LM Studio, so this isn't a local-model-specific limitation). The same research is equally clear that *unbounded* rounds are a real failure mode, not just a cost concern: extending a debate measurably increases the odds answers drift from the original question rather than keep improving, and a controlled 2025 comparison found that once compute is equalized, a single well-resourced call can match multi-agent debate's gains — the value is specifically in cross-checking, not in more rounds. Capped at exactly one: every dispatched specialist sees every other's first-pass result once, may revise once, and that revision is final — the lead judges from post-review results, never raw drafts, and there's no mechanism for a specialist to respond to a revision, which is what keeps this from becoming the open-ended version the research warns against.

**Make the review's reasoning visible, not just its effect**: the first version had a specialist silently rewrite its own answer with no visible trace of why — reading as "this one ignored the others" for any specialist whose answer didn't change, even when it had genuinely reviewed the material and correctly decided nothing needed to change. Split the cross-review output into a real explanation of what it thought of the others' results, then the answer body, separated by a literal delimiter string rather than asking for JSON (a local small model's free-text format-following was more reliable here than its JSON-schema-following) — and render the explanation as its own visible line regardless of whether the answer changed. A card whose answer didn't change now visibly says why ("reviewed, no correction needed") instead of looking indistinguishable from a card never reviewed at all — the same "silent success looks identical to silent failure" trap as elsewhere in this skill, at the UI layer instead of the pipeline layer.

**Visual representation, and where the line actually is**: asked to represent the exchange the way a reference multi-agent product (connect-ai) does — checking what that product actually ships confirmed it's a fixed sprite-art avatar per character plus a text speech bubble, not a live-generated image per turn; there's no image-generation step in that pipeline either. Matched the same shape with what was already available (a stable per-agent emoji as avatar, paired with the real cross-review comment text in a speech-bubble turn, appended as each specialist's review actually completes rather than all at once) — genuine parity with the reference product's actual mechanism, not a lesser version of it. **General lesson for "can you make it look like X" requests about a flashy reference product**: check what X actually does mechanically before assuming it needs new infrastructure — it's often built from much simpler, already-available pieces than its visual impression suggests.

## A real bug: a bullet/numbered list item silently splits into fake table columns once it contains any inline element

Found across several answer-quality complaints in the same project before the actual cause was isolated — reported repeatedly as "the chatbot is drawing a broken table" when no table markdown was ever present in the underlying text. The list-rendering CSS put `display: flex` directly on `<li>`, with the bullet/number as a `::before` pseudo-element positioned by flex layout — fine for a list item that's pure text, and silently broken the moment an item contains its own child element, because flexbox treats every top-level child of a flex container as its own flex item: the bullet, a `<strong>` tag, and the plain text node after it become three separate boxes laid out in a row instead of one flowing paragraph. Since "**label:** explanation" is close to the single most common shape a model produces for a bullet list, this fired on a large fraction of real answers without touching a single line of the LLM-facing prompt — every "make the formatting less broken" prompt iteration was chasing a bug that lived entirely in CSS.

**The fix**: switch from `display: flex` + flex-positioned bullet to `position: relative` + `padding-left` on the `<li>`, and `position: absolute` on the bullet pseudo-element — this removes flex layout from the `<li>`'s own content entirely, so mixed text+element content flows as one normal paragraph regardless of what's inside it. Apply to every list variant sharing the same pattern (bulleted, numbered, nested), not just the one where it was first noticed.

**General lesson**: when an AI-generated answer's *rendering* looks structurally wrong in a way that doesn't match what the model actually wrote, check the CSS handling markdown-to-HTML conversion before assuming the model's output or the parsing logic is at fault — `display: flex` on any element whose content isn't guaranteed to be a single text node is a specific, easy-to-miss trap, and it looks exactly like a model/parsing bug from the outside because the symptom is inconsistent and content-dependent.

## A related bug: retrieval that reads the chat message but not the caller's own already-known context

Found in the same CRM: a question about "that customer" and their symptom never named the actual product they'd bought (the shop owner already knew it). Domain-scoped search (§12) worked exactly as designed on the words actually in the message — the message just never contained the one word (a brand name) that would trigger the right domain's retrieval. The fix wasn't a smarter query, it was noticing the caller already had the missing information in a different field it already reads for every prompt (the customer's own purchase record) and feeding that into the search query too, not just the raw chat text — the same "caller-supplied, not AI-inferred" instinct as §7, just supplying search terms instead of a context tag.

**A real, only-partially-fixable limitation found in the same pass**: this only helps when the source record's text actually contains the brand name as an isolable token — real sales records in this project often glue a brand name directly onto other text with no separating space (a distributor prefix, a sample/batch number), and a keyword search that only tokenizes on whitespace can't pull a known term out of a longer unbroken string. **General lesson**: before concluding a retrieval gap needs a smarter query or classifier, check whether the caller already holds the missing context in a field it already has access to — but recognize this class of fix inherits the data-entry quality of whatever field it reads, and document that as a real, not fully code-fixable, limitation rather than continuing to chase it with cleverer string matching.

## What not to do

- Don't skip §5 to save a round-trip. It's designed to *not* cost a round-trip — fold it into the structuring call.
- Don't reach for an embedding model/vector DB before trying §3's keyword+graph approach. It's simpler, faster on local hardware, and the reference system runs on it in production.
- Don't force Self-RAG's grounded/guess tagging on every single message — reserve it for answers that are actually drawing on the wiki.
- Don't auto-structure without the confirm step in §2 — a quick "save this?" is cheap; retroactively cleaning bad notes out of a graph that's already been traversed and promoted into `verified.md` is not.
- Don't wait until a second tenant/channel actually causes a visible mix-up to add §7's context tagging — retrofitting it means re-tagging every existing note; adding the field from day one costs nothing since it can just stay empty until it's needed.
- Don't make Self-RAG a checkbox-only feature if the project already has a "should I search live" heuristic elsewhere — reuse that pattern for auto-detection rather than shipping one more toggle for the user to manage.
- Don't assume a `max_tokens` budget sized for the expected output length is still enough once the local model is reasoning-capable. On an OpenAI-compatible API, a reasoning model's hidden "thinking" tokens (surfaced as a separate `reasoning_content`/`reasoning_tokens` field) draw from the *same* budget as the actual answer — the model can burn the whole budget thinking and emit nothing usable. Measured in the 루카루카 안경원 CRM (2026-09-10): swapping to a 12B reasoning-capable local model made a single structuring call spend ~2,500 of its token budget on hidden reasoning before writing ~475 tokens of actual JSON, taking 200–280 seconds — both well past a 240s timeout / 8192-token budget that had been sized for a smaller non-reasoning model and had been working fine until the swap. Size both generously, and re-check them after swapping the local model, rather than assuming settings tuned for one model transfer to another.
- Don't extend the local structuring model into agentic browsing/tool-use just because it structures text well — the two are very different capability bars, and it's tempting to reach for "give it browser tools too" once ingestion is working. A local reasoning model that takes 200–280 seconds for one single-shot text→JSON call would need that same per-step latency (or worse) at *every* step of a multi-step browse-decide-click loop, and small/local models are also far less reliable at multi-step tool orchestration than a frontier model — errors compound across steps instead of being caught once. Keep the local model doing single-shot judgments (structure this, verify this, is this blocked) and leave multi-step navigation/login-wall handling to whatever agent — a human driving a browser, or a frontier-model agent — is actually capable of it.
- Don't detect "is this page part of a paginated series" by looking only at URL structure (same path, one differing query param) — a link to a completely different category on the same platform often matches that shape too and will be misidentified as another page of the current listing. Cross-check against the link's own visible text (a real page-number link's clickable text *is* the page number).
- Don't trust "be specific, don't summarize" alone to stop a model from compressing a long repeated list (a price list, a spec table) into a handful of named examples plus range buckets — that's the model's default instinct once a list gets long, no matter how the general instruction is worded. Name the shape explicitly ("if the source is a repeating item list, transcribe every item, no ranges/examples") and verify by counting a marker in the source against the same marker in the output — a summarized note reads more polished than an exhaustive one, so skimming it won't catch the gap.
- Don't store a gated site's username/password server-side to automate ingestion, and don't assume the user being logged into *their own* browser helps a server-side fetch — it never does, since that fetch is a separate, cookie-less request regardless of what's logged in elsewhere. Capture a session instead of a credential: a one-time login in a visible browser window the human types into directly, saved as cookies/storage-state, reused (and eventually re-captured when it expires) by later automated fetches. The code should never see the password at any point in this flow, only the session that comes out the other side of it.
- Don't build active bot-detection evasion (headless-fingerprint spoofing, etc.) into an unattended/repeatable ingestion pipeline just because a site blocks it. Found 2026-09-11: `ray-ban.com` returns Akamai's block page to both a plain `requests.get()` *and* a real headless Chromium via Playwright — confirming the block isn't "no real JS execution," it's deliberate anti-automation detection — while the exact same URL loads fine through an interactive browser tool driven by an agent (e.g. Claude's own browser pane). That gap is real and worth using, but the fix is "have a human/agent browse it manually and hand-feed the result through the same ingestion function," not "make the automated pipeline look more human." Deliberately evading a site's intentional anti-bot measures is a different category of fix than the JS-rendering/redirect/iframe fixes above — those work *with* how the site is built; evasion works *against* how the site chose to defend itself — and that category shouldn't be built into code that runs unattended and repeatedly.
- Don't assume a smaller or domain-specialized local model will outperform an already-validated general-purpose one on a specific pipeline task just because it's marketed for something adjacent (an "agentic" model, a "marketing/coding fine-tune"). Directly A/B tested 2026-09-11 against the real category-link-classification task (§9) with a fixed, known-ground-truth input: a dedicated 4B agentic model produced *no output at all* (burned its entire budget on hidden reasoning tokens); two Gemma-4 E2B/E4B variants matched on correctness but added several false positives each versus the baseline; a marketing/coding fine-tune was fastest but had the *worst* precision and leaked raw reasoning-channel markers into the content field instead of using the API's `reasoning_content` field properly. None beat the already-deployed general-purpose 12B model on this task. The lesson isn't "bigger always wins" (§"A fifth real bug"'s per-sub-task model sizing in [[self-improving-agent-strategy-memory]] shows the opposite in other cases) — it's that a plausible-sounding candidate (smaller, "agentic," domain-tuned) still needs a real A/B test against the actual task with actual ground truth before swapping it in; don't trust a model card's framing over a measured result.
- Don't conclude "the local/small model just can't do this" and stop — research first (a paper, a comparable project's actual code, published prompting technique) before treating anything as a hard capability limit. Every instance of this in this project so far turned out to be a fixable prompt/architecture issue, not a model ceiling: chat fabrication was fixed with a second verification call, rigid over-formatted answers were fixed by *removing* instructions rather than adding stronger ones (§11), and "compare across brands" was fixed with a cheap classification call plus per-entity retrieval — none of these needed a bigger or different model, all of them needed a better-researched fix to the existing one.
- Don't respond to "the model won't stop doing X even after I told it not to" by writing a stronger, more emphatic version of the same instruction and stacking it onto an already rule-dense prompt (§11's twelfth real bug) — check the total instruction count first. A system prompt is a shared attention budget; per-rule adherence measurably drops as more rules pile up (arXiv:2509.14404), so a prompt that's already carrying several correctness-critical rules (honesty, grounding, privacy) may need *fewer* stylistic rules to make room, not one more emphatic stylistic rule competing with the ones that actually matter more.
- Don't let a cross-review/refinement step inherit a first-pass grounding rule ("don't answer past your own domain's data") unmodified (§13). That rule is correct for original retrieval and wrong for the one step whose entire job is synthesizing across a neighboring domain's already-retrieved material — a rule correct at one pipeline stage can be actively wrong carried unchanged into a different stage with a different purpose. Check every reused instruction against the *new* stage's actual job, don't assume "it was correct before" means "it's still correct here."
- Don't let unbounded multi-agent "keep discussing until they converge" sound harmless just because *some* rounds of cross-checking help (§13). Real 2025 research shows extended debate rounds measurably drift from the original question rather than continuing to improve, and that a single well-resourced call can match multi-agent debate's gains once compute is equalized — cap review at exactly one round and treat the cap as a correctness decision backed by evidence, not a cost-saving shortcut you'd remove if latency stopped mattering.
- Don't put `display: flex` directly on a list item whose content isn't guaranteed to stay a single plain-text node. Any inline element inside it (a `<strong>` tag from the extremely common "**label:** text" pattern) becomes its own independently-wrapping flex item, producing a squeezed multi-column look that reads exactly like a broken table even though no table markdown exists anywhere in the source — check the CSS before chasing this as a model or markdown-parsing bug.
- Don't assume "silent = no error" during a batch migration onto a new schema field (§12). A retry/correction prompt used when content fails its own quality check often has a field list separately maintained from the main prompt's, and a schema addition applied to one but not the other silently drops the new field exactly on the records that needed a second pass — grep every prompt claiming "same format as before" and confirm its field list is actually current.
